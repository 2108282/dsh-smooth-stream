# 后台恢复修改说明 — v0.10.4-local.2

- 插件包版本：`0.10.4-local.2`
- Git 分支：`0.2.3`
- 记录日期：2026-11-22
- 范围：本对话对 WebView 后台恢复、吐字调度与隐藏内容排空的修改。

> 分支名称与插件包版本是两个概念。本记录不宣称已经完成所有 DSH 0.2.3 场景的兼容性或实机帧率验证。此次提交保留了仓库此前已有的本地未提交修改；下文仅将本对话新增的修复归为本次变更。

## 1. 取消固定 40ms 提交等待

助手正文与通用 DOM 吐字的限速追赶不再跳过不足 40ms 的动画帧，改为按实际动画帧分配字符预算。

以下规则保持不变：

- 追赶每次最多提交 16 个 Unicode 码点。
- 原有速率参数、恢复方式和用户设置不被重置。
- 长帧只按最多 80ms 积分，不累计整字符的补偿债务。
- 不承诺 120Hz 屏幕对应每秒 120 次文字提交。

## 2. 重同步完成且无积压时退出恢复

删除原有“等待以后第一次新文字”的恢复锁存逻辑，改为以 Session 自己的同步状态判断是否已经恢复。

- 借用现有 Session binding，不额外 retain Session 或建立第二条流。
- 断连及连接 generation 变化时等待新的替换基线。
- 连接就绪不等于 Session 基线已经同步。
- 接受替换基线后，当前队列排空即可退出恢复。
- 空基线、内容未变化的基线也能结束同步等待，不要求再来一段文字。
- 终止性的 Session 同步错误释放空的恢复等待。
- 同步通知只唤醒真正停在同步等待阶段的客户端，不重置正在追赶的吐字时钟。
- 普通 Session 快照更新不会因为 `openState` 未变化而反复唤醒恢复回调。

## 3. 收起内容不形成不可见的长时间吐字门禁

### 思考内容

- 以官方实际披露行的展开状态为依据，不重复调用官方独立 disclosure Hook。
- 收起的思考直接同步已有源文本，不逐字消耗不可见的字符积压。
- 官方完全不展示的 signature 内容及 signature 前缀直接同步。
- 多个思考块按实际可显示的行映射，避免被过滤的块造成索引错位。
- 手动展开时显示已有完整快照，只对随后到达的可见新文字继续动画。
- 跳过整块文字前实时检查缓存的披露行、`data-expanded` 和祖先隐藏状态，防止“刚展开就收到新文字”时被陈旧的收起状态直接跳过。
- 官方自动展开、手动选择、Turn reset 与标题 shimmer 保留。

### 工具与其他通用聊天节点

- 隐藏、折叠、条件卸载的详情不逐字等待。
- 增加外部祖先容器折叠检测，处理整个 Turn 被隐藏的情况。
- 展开已有详情是快照展示，不从头补播。
- 可见工具摘要仍使用文字动画预算。
- 清理 Observer、Session/连接订阅及缓存行节点；静态历史不额外订阅恢复或披露观察。
- 不监听 FollowHost 内部逐帧 transform 样式，避免滚动帧触发无谓扫描。

### 队列范围

聊天节点中的运行命令、上下文注入、其他 Agent 输出会参与节点顺序队列。作为聊天节点显示的模型错误走同一通用规则；宿主全局错误与通知不进入聊天吐字队列。

独立 Todo 面板、过程组标题、底部运行状态和输入区状态不纳入这套队列。回复正文中的任务清单属于可见正文，正常吐字。

这些分类没有逐类覆盖所有真实 WebView 展示形式；结论来自代码规则和已有自动化回归，不是实机逐项验证。

## 4. 积压如何计算，为什么参数固定也可能卡顿

积压不是把整个页面所有卡片的文字简单相加：

- 助手节点以当前投影源文本的码点数减去已显示的码点数计算。
- 通用 DOM 节点以该根容器中待显示的可见文本节点累计剩余码点数；同一工具树共享预算并按 DOM 顺序消费。
- 节点之间另外用 Session/Turn/Step 顺序门禁决定先后，不使用全页面总字数分配统一预算。
- 隐藏范围同步后不再占长期文字积压。

普通流式模式本来就含有队列压力、自适应速度和完成后排空逻辑，设置中的上限不等于无条件固定的实际字速。

限速追赶的预算近似如下，最后只携带小于一个字符的小数债务：

```text
cps = min(400, max(120, maxRevealCps × revealScale × 1.5))
本帧字数 = min(当前剩余积压, 16, floor(cps × min(帧间隔, 80ms) / 1000 + 小数债务))
```

所以在限速追赶中，大积压本身不会把计划字速调低，但会延长排空所需时间。实际吞吐还受主线程和动画帧交付约束：React、Markdown、DOM 和布局工作过多时，动画帧可能延迟；每帧 16 字的上限又限制慢帧下的追赶吞吐。例如每秒只有 10 次提交，理论上最多 160 字/秒。这不是设备实测。

本次确证并修复的额外限速来源是固定 40ms 等待、空恢复锁存、不可见详情债务，以及普通 Session 更新反复重置恢复时钟。并未依据猜测进一步更改用户物理参数。

## 7. 建议实机复测

1. 刷新页面，使用限速追赶；生成长回复时切到后台 20–30 秒再返回，观察正文是否持续前进。
2. 收起思考和工具详情，确认后续可见回复不为不可见的长内容等待。
3. 生成中手动展开，确认已有内容直接显示、新到达的可见文字仍动画。
4. 若仍异常，记录恢复方式、后台停留时间、卡住的节点类型及持续时间，再按实机证据定位。
